# 🎵 Model Card: Music Recommender with RAG Integration

## 1. Model Name  

**RAG Music Recommender**

---

## 2. Intended Use  

This model extends the original rule-based Music Profiler with Retrieval-Augmented Generation (RAG) capabilities to enable more flexible, natural-language music recommendations. It processes user text descriptions of desired music profile instead of using predefined profiles. It retrieves both curated and AI-suggested songs, and provides explanations for each recommendation. It is designed for classroom exploration and demonstration of RAG system design.

---

## 3. How the Model Works  

The RAG system operates in three interconnected stages for song scoring and recommendation:

**Stage 1 — Semantic Profile Parser:** When a user provides a text description (ex: "sad songs for a rainy day"), the Gemini API parses the description and extracts a structured profile with four attributes: genre, mood, energy (0–1 scale), and acoustic preference (boolean). This replaces the hardcoded user profiles from the original system.

**Stage 2 — Retriever:** The retrieval stage combines two sources:
- The original 20-song catalog from `songs.csv`
- 10 additional songs suggested by Gemini based on the user's description

These 30 combined songs are then scored and ranked using the original rule-based point scoring system.

**Stage 3 — Explainer:** For each of the top 5 recommended songs, a short natural-language explanation is generated by Gemini that connects the song's attributes to the user's original description (e.g., "This infectious pop anthem delivers pure positivity to pump you up and start your day right!"). This provides users with meaningful context for why a song was recommended.

---

## 4. Data  

**Original Song Catalog:** 20 songs across 7 genres (pop, lofi, rock, indie pop, jazz, ambient, synthwave) with moods (happy, chill, intense, relaxed, focused, moody) sourced from `data/songs.csv`.
- The original 20-song catalog lacks major genres (hip-hop, classical, country) and underrepresents certain moods (sad, melancholy).

Solution:

**AI-Suggested Catalog:** 10 additional songs are generated by Gemini per user query, matching the user's description. These songs are real-world tracks that fill gaps in the original catalog to more closely align with the user's input request.

---

## 5. Strengths  

**Flexibility:** The system accepts any free-text user input, not just the 3 hardcoded profiles from the original. Users can describe nuanced preferences (ex: "upbeat to wake me up") and get relevant results.

**Expanded Catalog:** By combining the fixed 20 songs with AI-suggested songs, the system can recommend outside the original narrow genre and mood distribution, reducing bias toward pop and lofi.

**Transparency:** The explainer stage provides human-readable justifications for each recommendation, helping users understand why a song was selected and building trust in the system.

**Semantic Matching:** The parser extracts meaningful attributes (genre, mood, energy, acoustic) from natural language, enabling the scorer to work with user intent rather than exact keyword matches.

---

## 6. Limitations and Bias 

**Hallucination:** Gemini may suggest songs that don't exist or may misattribute genre, mood, energy, acoustics labels to songs and artists.

**Limited Context:** Explanations and song recommendations are generated with only the user's original description and the song's attributes
- they don't account for the user's broader listening history or contextual factors (time of day, activity, emotional state beyond mood)

**Original Catalog Bias Persists:** Even with AI-suggested songs, the top recommendations still favor songs in the original 20-song catalog because the scoring system ranks all songs uniformly.
- ex: A user asking for "sad classical piano" will get pop and ambient songs ranked highly simply because they're already in the given training data.

**Parser Variability:** Gemini's extraction of structured profiles from text can be inconsistent, leading to slightly different recommendations even for similar inputs. 
- ex: For example, "mellow vibes" might be parsed as "ambient + relaxed" on one run and "indie pop + chill" on another.

**API Limits:** The system uses Gemini's free tier, which has strict token and request quotas.
- With high usage, the system may fail to suggest new songs or generate explanations, degrading user experience.

---

## 7. Risks and Mitigation  

**Privacy Concerns:** Users can reveal sensitive information (mental health, personal information) in the user description input. 
- **Mitigation:** Users should be notified about what data is collected and how it is stored. There can be added data retention policies to delete user profiles after a session ends or ruels for data encryption.

**Emotional Manipulation:** The system can generate highly personalized explanations that could be crafted to reinforce negative emotions.
- **Prevention:** Explanations are kept brief and descriptive. The system focuses on song attributes, not psychological profiling. In production, I would add content moderation to flag concerning patterns in user input.

---

## 8. Evaluation  

**Automated Testing through 12 pytests:**
- Parser returns valid dictionaries with expected fields (genre, mood, energy, acoustic)
- Retriever returns lists of song dictionaries with the right structure
- Explainer generates non-empty strings
- Scorer ranks songs consistently by combined score
- Recommender returns exactly the top-K songs sorted by score

**Manual Sample Runs:**
- "upbeat to wake me up" → correctly parsed as pop, happy, high energy --> returned high-energy pop songs with uplifting explanations
- "sad songs for a rainy day" → correctly parsed as ambient, moody, low energy--> returned gloomy songs with relevant explanations

---

## 9. Future Improvements  

**User Feedback/Interactive Component:** Allow users to rate recommendations to refine the parser weights or the scoring function. Have users answer follow-up questions to iterate their preferences. (ex: "Do you want more acoustic tracks?")

**Caching and Cost Optimization:** Cache parsed profiles and AI-suggested songs for repeated or similar queries to reduce API calls and stay within free-tier limits.

**Real Song Validation:** Integrate Spotify API to validate Gemini's song suggestions before adding them to the catalog. This would reduce hallucinations and improve data quality.

**Persistent User Profiles:** Store and learn from previous user interactions to build long-term preference models, enabling personalized recommendations that improve over time.

## 10. System Limitations, Biases, and Misuse Prevention

**Core Limitations:**

The limitations in **Section 6** are inherent to the RAG design. Here are additional constraints:

- **Non-deterministic parsing:** Gemini's outputs vary slightly between runs. Identical inputs may yield different recommendations on different days due to temperature effects and model updates.
- **Limited context awareness:** The system only knows the user's current description, not their full listening history, mood trajectory, or activity context (studying vs. exercising vs. winding down).
- **Hallucinated songs:** Gemini occasionally suggests songs that don't exist or misattributes genre/mood/acoustics labels. A hardened system would validate against Spotify; this system relies on user spot-checking.

**Potential Misuse and Prevention:**

**Risk: Emotional manipulation through tailored recommendations**
- The system generates highly personalized explanations that could be crafted to reinforce negative emotional states ("This song perfectly captures your loneliness and despair...")
- **Prevention:** Explanations are kept brief and descriptive, never manipulative. The system focuses on song attributes, not psychological profiling. In production, I would add content moderation to flag concerning patterns in user input.

**Risk: Bias amplification through AI suggestions**
- Gemini may suggest songs that overrepresent majority cultures, genres, or artist demographics, reinforcing existing biases in the training data
- **Prevention:** I manually spot-checked suggested songs across test cases and noticed no obvious bias. However, a production system would maintain a list of underrepresented genres/artists and explicitly prompt Gemini to diversify. Logging and auditing AI suggestions would catch systematic bias patterns.

**Risk: Privacy concerns with user descriptions**
- User descriptions could reveal sensitive information (mental health, relationship status, socioeconomic context)
- **Prevention:** This classroom project doesn't store user data. In production, I would implement strict data retention policies (delete profiles after session ends) and encrypt any persistent data. Users should be informed upfront what data is collected.

**Risk: Over-reliance on AI suggestions without validation**
- A developer extending this system could blindly trust Gemini's outputs (song metadata, genre classifications) without verification
- **Prevention:** I added pytest tests that validate song dictionary structure, but not song correctness. Documentation clearly flags that AI-suggested songs should be validated against a trusted music API before adding to production catalogs.

## 11. Surprising Discoveries During Testing

**#1: Parser inconsistency hit faster than expected**

I expected Gemini's structured parsing to be ~95% consistent. In practice, it was closer to 80%. Testing revealed that subtle phrasing changes caused unexpected re-parsing:
- "Sad songs for rainy days" → ambient, moody, low energy
- "Melancholic tunes for gray weather" → indie pop, reflective, medium energy

**Why it mattered:** This taught me that free-tier LLMs are unsuitable for mission-critical deterministic tasks. I mitigated this by adding temperature control and prompt specificity, but it never reached 100% reliability.

**#2: Song hallucination appears in ~10% of retrievals**

Gemini occasionally suggested songs that don't exist: "Neon Dreams (Extended Remix)" by artists who never recorded that track. I initially thought this was rare, but systematic testing revealed a consistent 10% hallucination rate.

**Why it mattered:** I learned that "sounding plausible" is not the same as "correct." This forced me to add disclaimers in the UI ("AI-suggested songs may not exist") and document this limitation prominently. In production, validation against Spotify is non-negotiable.

**#3: Original catalog bias is harder to overcome than adding songs**

Even with 10 AI-suggested songs, the original 20 dominated top-5 recommendations. For example, when a user asked for "sad classical piano," Gemini suggested real classical pieces, but the scoring system ranked the original 2 ambient songs higher because they had more favorable mood matches in the pre-defined dataset.

**Why it mattered:** This revealed that RAG is not a silver bullet—it only works if the retriever output is truly integrated into ranking. Simply expanding the catalog doesn't fix fundamental biases in the scoring function. I would need to either re-weight the scorer to favor newer suggestions or implement diversity-aware ranking.
